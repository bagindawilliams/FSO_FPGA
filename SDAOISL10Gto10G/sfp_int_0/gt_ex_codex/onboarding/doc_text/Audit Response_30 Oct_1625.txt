           Poin kedua ini sangat penting untuk memastikan sistem kita tidak hanya lulus untuk 1 paket 2.000 Byte, tetapi juga tangguh terhadap gangguan dan berbagai ukuran paket (multi-data):

             1. Reassembly (ethernet_frame_reassembly.v) — B05/B06 + B03/B04/B07/B08:

                   ◦ B05 (Validasi Magic 0xAB): Kita pulihkan pengecekan frame_magic_valid: pada fso_word_idx == 0, jika s_axis_fso_tdata[31:24] != 8'hAB, maka seluruh sisa kata di frame FSO tersebut (1..476) ditolak agar frame rusak tidak pernah masuk ke buﬀer Ethernet.

                  ◦ B06 (Pembuangan Paket Parsial saat Urutan DATA Terputus / Sequence Skip): Paket 2.000 Byte membutuhkan 2 frame DATA (seq = 0 untuk 1.900B pertama, dan seq = 1 untuk 100B sisanya). Kita pulihkan register expected_fso_seq [9:0] dan pointer pengaman

                    sehingga data Ethernet yang kebetulan bernilai 0x00000000 tidak pernah dianggap sebagai padding.

           POIN 3 AUDITOR (image_3e0fe2.png): "3. Perbaikan ARQ jika digunakan dalam demo"

           Keempat poin di gambar kedua ini sangat bersih dan mudah kita selesaikan di arq_tx_controller.v, arq_ddr4_wrapper.v, arq_rx_reorder_ddr4_wrapper.v, dan ethernet_fso_framer.v:

             1. B10 — ACK salah membebaskan tracker (arq_tx_controller.v):

                  ◦ Kita hapus pencocokan alamat slot ﬁsik {track_txfn[i][15:4], track_slot[i]} == rx_rxfn_in pada blok penerima ACK/NAK, dan gunakan murni if (track_valid[i] && (track_txfn[i] == rx_rxfn_in)). Dengan demikian, ACK 17 tidak akan pernah
                    membebaskan tracker milik TXFN = 16 (arq_false_ack.sv langsung aman)!

             2. B11 — Delete bersamaan dengan Read/Write (arq_tx_controller.v & arq_ddr4_wrapper.v):

                  ◦ Ketika sebuah ACK (atau max-retry drop) yang meminta ddr4_delete_req terjadi pada siklus clock yang sama persis dengan eksekusi S_EXEC_RETX (ddr4_read_req) atau S_EXEC_DATA (ddr4_write_req), arq_tx_controller.v menampung permintaan hapus tersebut ke
                    dalam register antrean 1-siklus (pending_delete_req & pending_delete_addr) dan mengeksekusinya tepat 1 siklus kemudian (saat state berada di S_WAIT_FRAME dan bus ddr4_addr sedang bebas)! Selain itu, ddr4_addr selalu membawa track_txfn 16-bit asli sementara
                    arq_ddr4_wrapper.v mencocokkan tag 16-bit penuh tersebut di tabel CAM-nya. Hasilnya: pada arq_ack_retx_shared_address.sv, tag 0 dihapus dengan benar dan tag 16 tetap utuh untuk dibaca ulang!

             3. B13 — Recovery missing frame (arq_rx_reorder_ddr4_wrapper.v):

                  ◦ Agar pemulihan frame yang hilang (missing_holdoff_cnt) tidak hanya bergantung pada kedatangan frame IDLE/MGMT (reorder_timeout_without_idle.sv), kita tambahkan autonomous frame-duration tick (setiap 1 periode frame = 780 siklus clock @ 312.5 MHz, atau setiap
                    kedatangan frame apa pun) ketika any_ooo_buffered == 1. Dengan demikian, baik ada IDLE/MGMT maupun ketika jaringan hening setelah mengirim DATA 1 dan DATA 3, expected_txfn tetap pulih secara deterministik setelah waktu holdoﬀ × max_retry terlampaui!

             4. B17 — Antrean ACK (ethernet_fso_framer.v):

                  ◦ Pada antrean FIFO 8-entri ack_q di ethernet_fso_framer.v baris 190, kita ubah syarat masuk dari (ack_q_count < 4'd8) menjadi ((ack_q_count < 4'd8) || ack_q_pop) sehingga ketika antrean sedang penuh (8) dan 1 entri dikeluarkan pada siklus yang sama
                    (ack_q_pop = 1), event ACK baru tetap diterima masuk tanpa ada yang terbuang.
